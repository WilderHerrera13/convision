# Plan 21-08: Patient + Appointment — most complex domains

## Objective

Patient and Appointment are the highest-complexity migrations:

- **Patient**: currently uses `parseApiFilters` with `s_o=or` mode. The `patientFilterAllowlist` is a `map[string]string` with per-column operators (ILIKE for name/email/phone/identification, = for status/gender). Frontend sends 5 text fields via s_f/s_v/s_o=or. Replacement: single `Search string` field with multi-column OR ILIKE in repo.

- **Appointment**: currently uses `parseAppointmentApiFilters()` (a wrapper around `parseApiFilters`) plus 4 additional special keys set directly in the handler (`_start_date`, `_end_date`, `_patient_search`, `_attended_by`, `_pending_report`). Each maps to non-trivial SQL logic. Replacement: explicit named fields on `AppointmentFilter`.

This plan must be executed sequentially after 21-07 (listed in depends_on). 21-07 does not touch handler.go, so no file conflicts exist; the sequential constraint exists only to ensure all prior waves are complete before the most complex migrations run.
