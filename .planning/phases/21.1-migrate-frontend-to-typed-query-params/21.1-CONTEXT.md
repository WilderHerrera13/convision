# Phase 21.1: Migrate Frontend to Typed Query Params - Context

**Gathered:** 2026-05-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Migrate the React frontend (`convision-front/`) off the legacy `s_f`/`s_v`/`s_o=or` JSON-array filter contract and onto the typed query-param shape that Phase 21 introduced on the Go backend. After this phase, no frontend code emits `s_f`/`s_v`/`s_o` params, and every list/search call sends the same flat `?key=value` shape that the typed `domain.<Entity>Filter` structs bind via `c.ShouldBindQuery()`.

In scope:
- All ~15 frontend service files that currently build `s_f`/`s_v` arrays
- Both list-page services (patient, appointment, sale, quote, order, expense, purchase, payroll, service order, cash transfer, daily activity, clinical history, prescription) and catalog/dropdown services (lens, brand, catalog, supplier, material, treatment, category, inventory, laboratory, user)
- Frontend audit of any non-`s_f`/`s_v` ad-hoc query-param senders that don't match the typed filter shape
- Backend retirement-verification task: grep + assertion that no caller sends legacy params

Out of scope (deferred):
- Adding a backend middleware that 400s on legacy params (see Deferred)
- Refactoring response shapes (this phase only changes request shape)
- Codegen toolchain for emitting TS types from Go domain structs

</domain>

<decisions>
## Implementation Decisions

### Scope & sequencing
- **D-01:** Migrate all 15 service files in this single phase — finish the `s_f`/`s_v` retirement in one cycle; no per-domain split.
- **D-02:** Single PLAN.md for the whole migration (task-level granularity inside one plan).
- **D-03:** Both list pages and catalog/dropdown searches are in scope.

### TypeScript filter contract
- **D-04:** One typed interface per entity, mirroring the Go `domain.<Entity>Filter` struct (e.g. `PatientFilter`, `AppointmentFilter`, `SaleFilter`). No generic `Record<string, any>`; no codegen toolchain.
- **D-05:** Filter interfaces co-located with each service file (export from `patientService.ts`, etc.) — matches existing service conventions.
- **D-06:** Multi-field text search expressed as a single `search` string field on the frontend; the backend fans out OR-ILIKE across the columns it configured (Phase 21-08 PatientFilter precedent). FE never sends per-field arrays for text search.

### Migration strategy & rollback
- **D-07:** Direct cut-over per service: delete `s_f`/`s_v`/`s_o` construction, add the typed filter shape in one change. No dual-emit transition helper — backend already accepts the new shape (Phase 21 graceful degradation), so no dual-emit is needed.
- **D-08:** Verification = network-diff snapshot before/after. Capture URL+response for representative searches on each migrated page before the change, compare after. No new automated test investment in this phase.
- **D-09:** Phase-level revert if production breaks — single atomic phase commit (or tightly clustered commits) so a regression can be rolled back as a unit.

### Backend cleanup follow-up
- **D-10:** Include a backend retirement-verification task in 21.1: grep `convision-front/` for any remaining `s_f|s_v|s_o`, grep `convision-api-golang/` for any residual reader, and assert both return zero matches. (`parseApiFilters` is already deleted in Phase 21-10; this just locks the retirement.)
- **D-11:** Audit all list calls (not just `s_f`/`s_v`) — reconcile every frontend list/search call against the Go `domain.<Entity>Filter` struct fields, surface any drift, and either align it or document the divergence. Catches drift beyond JSON-array params.

### Special cases (carry forward from Phase 21 backend work)
- **D-12:** Appointment pseudo-keys (`_start_date`, `_end_date`, `_patient_search`, `_attended_by`, `_pending_report`) become typed fields on `AppointmentFilter` per Phase 21-08 — the FE must use the typed names, not the underscore-prefixed map keys.
- **D-13:** `branch_id` is injected by middleware on the backend (`form:"-"`); frontend should NOT send `branch_id` as a query param — `X-Branch-ID` header (existing branch middleware) remains the source of truth.

### the agent's Discretion
- Naming convention for filter interfaces (e.g. `PatientFilter` vs `PatientListParams`) — pick whichever reads cleaner per service; default to the Go struct name (`PatientFilter`)
- Exact filename split if a single service file gets large (inline vs `patientService.types.ts` sibling)
- Internal helper functions inside services (e.g. `buildPatientFilter()`)
- Order of migration within the single plan (which service goes first)
- Snapshot tooling for network-diff verification (browser DevTools HAR vs scripted capture)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/services/ApiService.ts` — singleton axios wrapper used by every service; query strings flow through this
- `src/lib/axios.ts` — axios instance with base URL, auth interceptors, `X-Branch-ID` middleware
- `URLSearchParams` and inline query objects are already the dominant pattern in services (e.g. `searchParams.append(...)` in `lensService.ts`, plain object spreads in `patientService.ts`)
- React Query hooks in pages already pass typed params to services — only the inner service logic needs to change, not the calling pages (mostly)

### Established Patterns
- One service file per backend resource (`patientService.ts`, `saleService.ts`, etc.)
- Inline TypeScript params types co-located with each service (`SupplierListParams`, etc.) — extending this convention to typed filters keeps zero new structure
- Search debouncing handled at the page level via `useDebounce` hook — service receives a finalized search string
- All API calls go through `/api/v1/*` (backend dev port 8001 via Vite proxy)

### Integration Points
- 15 service files: `patientService.ts`, `laboratoryService.ts`, `lensService.ts`, `prescriptionService.ts`, `supplierService.ts`, `brandService.ts`, `userService.ts`, `catalogService.ts`, `appointmentsService.ts`, `clinicalEvolutionService.ts`, `clinicalRecordService.ts`, `purchaseService.ts`, `dailyActivityReportService.ts`, `categoryService.ts`, `inventoryService.ts`
- ~20 page-level callers (admin/* and receptionist/*) that may pass `s_f`/`s_v`/`s_o` strings into services — they should not be doing this; the migration must check whether the JSON-array shape is built in the page (need to extract to service) or in the service itself
- Backend list endpoints under `/api/v1/*` already accept the new shape; no backend changes are required for the migration itself (only for the verification task)

### Creative Options (within scope)
- Optional shared `buildQueryString<T>(filter: T): string` helper in `src/lib/` — could reduce duplication across services. Not required, agent's call.
- Could co-locate filter interfaces in a `*.types.ts` sibling per service if the service file gets long (existing convention: inline types). agent's call per service.

</code_context>

<specifics>
## Specific Ideas

- The backend's typed filter contract (Phase 21) is the **canonical wire format** — every TS filter interface must match the Go struct's `form:"..."` tags exactly. Treat the Go structs as the single source of truth.
- Phase 21-08 explicitly noted: "FE can keep sending [legacy params] until it migrates" — Phase 21.1 is that migration. The backend tolerance was a transition-period feature, not a permanent one (see D-10).
- Per-eye prescription range filters (Phase 21-09 `LensFilter`) use pointer fields on the Go side — these become `?sphere_od_min=0.5&sphere_od_max=2.0` style flat params on the FE.

</specifics>

<deferred>
## Deferred Ideas

- Backend middleware that 400s on `s_f`/`s_v`/`s_o` params — would force-break any forgotten caller. Belongs in a follow-up backend hardening phase, not 21.1 (per D-10 we lock retirement via a verification grep, not active rejection).
- Codegen toolchain to emit TS types from Go domain structs (e.g. tygo, tsgen) — adds toolchain complexity to a brownfield project; revisit if drift becomes a recurring pain point.
- Playwright/RTL regression coverage for filter UI — a worthwhile investment but out of scope for this phase (D-08 chose network-diff snapshots over automated tests).
- Refactoring response shapes or extracting list/search behavior into a generic hook — purely a request-shape migration; deeper refactors are separate work.

</deferred>
