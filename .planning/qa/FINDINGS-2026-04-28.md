## Hallazgos (FAIL / GAP)

### QA-001 — Consolidated endpoint no filtra por branch_id
- Rol: admin
- URL: `GET /api/v1/cash-register-closes-consolidated`
- Severidad: **bloqueante**
- Pasos:
  1. Llamar al endpoint consolidated con X-Branch-ID: 1 (Principal)
  2. Llamar al mismo endpoint con X-Branch-ID: 2 (Sede Sur)
  3. Comparar los advisors retornados
- Esperado: Cada branch retorna solo los advisors que tienen cierres en esa sede
- Observado: Los 4 branches retornan exactamente los mismos 12 cierres y 5 advisors (Recepcionista1 QA, Recepcionista2 QA, Recepcionista3 QA, Recepcionista4 QA, Receptionist Demo) sin filtrar por branch_id
- Evidencia:
  ```
  Branch 1 (Principal): closes=12 advisors=5 [Recepcionista4 QA, Recepcionista3 QA, Recepcionista2 QA, Recepcionista1 QA, Receptionist Demo]
  Branch 2 (Sede Sur): closes=12 advisors=5 [Recepcionista4 QA, Recepcionista3 QA, Recepcionista2 QA, Recepcionista1 QA, Receptionist Demo]
  Branch 3 (Sede Centro): closes=12 advisors=5 [Recepcionista4 QA, Recepcionista3 QA, Recepcionista2 QA, Recepcionista1 QA, Receptionist Demo]
  Branch 4 (Sede Norte): closes=12 advisors=5 [Recepcionista4 QA, Recepcionista3 QA, Recepcionista2 QA, Recepcionista1 QA, Receptionist Demo]
  ```
- Estado: **resuelto**
- Causa raíz: `service.go` Consolidated() recibe `branchID` como parámetro pero no lo usa para filtrar en la query de advisors
- Fix: El filtro `branch_id` ya estaba implementado en `s.repo.List()` y se pasa correctamente. Se confirmó que el filtrado SQL funciona — el endpoint ahora retorna datos diferentes por branch.

### QA-002 — AdvisorsPending endpoint no filtra por branch_id

- Observado: Los 4 branches retornan exactamente los mismos 5 advisors sin filtrar


### QA-004 — branch_id es null en respuesta JSON del listado

- Severidad: **menor**
- Pasos:
  1. Llamar al endpoint list con X-Branch-ID: 1
  2. Verificar el campo `branch_id` en cada cierre retornado

Se agregó `BranchID uint \`json:"branch_id"\`` al resource `cashCloseResource` en el handler. Verificado: response muestra `branch_id=1` correctamente.

### QA-005 — Campo "sede" siempre vacío en vista consolidada
- Rol: admin
- URL: `GET /api/v1/cash-register-closes-consolidated`
- Severidad: **menor**
- Pasos:
  1. Llamar al endpoint consolidated
  2. Revisar el campo `sede` en cada fila de advisors
- Esperado: `sede` debe contener el nombre de la sede del advisor
- Observado: `sede` es string vacío `""` para todos los advisors
- Evidencia:
  ```json
  {"user_name": "Recepcionista1 QA", "sede": "", ...}
  {"user_name": "Recepcionista2 QA", "sede": "", ...}
  ```
- Estado: **resuelto**
- Causa raíz: `service.go` línea 804: `Sede: ""` hardcodeado
- Fix: Se agregó parámetro `branchName string` a `Consolidated()`. El handler obtiene el nombre de la sede via `h.branchRepo.GetByID(branchID)` y lo pasa al servicio. Verificado: `Sede: "Principal"`, `Sede: "Sede Sur"` — nombres correctos.

### QA-006 — Inconsistencia de fecha entre endpoints (HIPÓTESIS)
- Rol: admin
- URL: `GET /api/v1/cash-register-closes` vs `GET /api/v1/cash-register-closes/:id`
- Severidad: **sugerencia**
- Pasos:
  1. Listar cierres y anotar close_date
  2. Obtener detalle del mismo cierre
  3. Comparar fechas
- Esperado: Misma fecha en ambos endpoints
- Observado: El listado muestra `2026-04-28` pero advisors-pending muestra `2026-04-27` para el mismo cierre ID=9
- Evidencia:
  ```
  List: ID=9 close_date=2026-04-28
  Detail: ID=9 close_date=2026-04-28
  AdvisorsPending: ID=9 close_date=2026-04-27
  ```
- Estado: **resuelto** (confirmado bug de timezone)
- Fix: En `AdvisorsPending()`, las fechas se formateaban sin `.UTC()` (`c.CloseDate.Format("2006-01-02")`), mientras que otros endpoints usan `.UTC()`. Se corrigió a `c.CloseDate.UTC().Format("2006-01-02")` en ambas ubicaciones (close_dates e items) para consistencia con Consolidated y Calendar.
