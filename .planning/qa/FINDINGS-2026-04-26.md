### QA-001
- Rol: specialist
- URL: http://localhost:4300/specialist/appointments (sidebar)
- Severidad: mayor
- Pasos:
  1. Login como specialist.
  2. Abrir el sidebar (click en "Expandir sidebar").
  3. Intentar hacer click en "Cerrar sesión" (botón inferior del sidebar).
- Esperado: Se cierra la sesión del usuario.
- Observado: El elemento de "Cerrar sesión" nunca es interactuable. El sidebar se cierra antes de que el click llegue al botón, o el ref deja de ser válido. La acción de `browser_click` retorna "Element not found". El bug afecta tanto a `browser_scroll`, `browser_highlight` como `browser_search`.
- Evidencia: Error repetido: `Error: Element not found: e46`. Sidebar colapsa con animación CSS antes de que el evento sea procesado.
- Estado: **resuelto** (2026-04-28)
- Fix: Se agregó botón de logout (`<LogOut>`) visible en estado colapsado del sidebar, junto al toggle de expansión. Ver `AdminLayout.tsx` lines 166-184.
- Impacto resuelto: El usuario ahora puede cerrar sesión incluso con el sidebar colapsado.

### QA-002
- Rol: receptionist / specialist
- URL: http://localhost:4300/specialist/appointments (y otras vistas con citas)
- Severidad: mayor
- Pasos:
  1. Crear una cita con hora 8:00 AM (hora local).
  2. Observar cómo se muestra la hora en la lista de citas del specialist.
- Esperado: La hora mostrada debe corresponder con la hora configurada en la creación (8:00 AM hora local).
- Observado: El specialist ve la cita a las 3:00 AM. El backend guarda en UTC (8:00 AM → 13:00 UTC), pero el frontend la despliega como hora UTC sin convertir a local, provocando un desfase de 5 horas (UTC-5).
- Evidencia: Cita creada "8:00 AM" visible como "3:00 AM" en la vista del specialist. Selector de fecha/hora en creación no incluye selector de timezone.
- Estado: **resuelto** (2026-04-28)
- Fix: Función `toLocalDate()` en `specialistAppointmentsColumns.tsx` simplificada. Se eliminó la lógica que agregaba `'Z'` a datetimes naive sin timezone, ya que `parseISO()` de date-fns v3 trata correctamente datetimes sin offset como hora local. La lógica anterior trataba incorrectamente fechas naive como UTC.
- Nota: El backend envía `scheduled_at` con sufijo `Z` (UTC). Con el fix, `parseISO` convierte correctamente UTC → local al formatear.

- Severidad: menor
- Pasos:
  1. Abrir formulario clínico de una cita.
  2. Ir a tab "Anamnesis".
  3. Intentar marcar/desmarcar checkboxes de antecedentes (ej. "Autoinmune").

- Esperado: Los checkboxes interactuables NO deben tener el estado `readonly` en el árbol de accesibilidad.

- Estado: **resuelto** (2026-04-28)
- Fix: Se agregaron `readOnly={false}` y `aria-readonly={false}` explícitos a los checkboxes de "Otras condiciones sistémicas" en `AnamnesisSection2.tsx` (línea 93), igualando el patrón ya usado en Secciones 4 y 5. Esto evita que el inspector ARIA reporte inconsistencia entre `readonly` y el estado `checked`.

### QA-004
- Rol: specialist
- URL: http://localhost:4300/specialist/appointments/:id/consultation
- Severidad: menor
- Pasos:
  1. Llenar el tab "Anamnesis" completamente.
  2. Hacer click en el botón "Siguiente →" al final del tab.
- Esperado: El sistema navega al siguiente tab (Examen Visual).
- Observado: El botón "Siguiente →" NO navega al siguiente tab. La navegación entre tabs sólo funciona haciendo click directo en las pestañas numeradas en la parte superior del formulario.
- Evidencia: Click en "Siguiente →" no produce cambio de URL ni de tab activo; el snapshot posterior muestra el mismo tab "Anamnesis" activo.
- Estado: **revisado** (2026-04-28)
- Análisis: El botón "Siguiente →" en Anamnesis es `type="submit"` que ejecuta `handleSaveAnamnesis()` → `upsertAnamnesis()` → `setActiveTab(1)`. Si el API call falla, se muestra toast de error y NO se navega (by design para no perder datos). La validación Zod requiere `reason_for_visit` no vacío. Si la API falla, el usuario se queda en el mismo tab sin navegación.
- Recomendación: Agregar indicador visual de error más prominente cuando el guardado falla.

### QA-007
- Rol: specialist
- URL: http://localhost:4300/specialist/appointments/:id/prescription-preview
- Severidad: mayor
- Pasos:
  1. Llenar el tab Prescripción con OD Esférico "-2.00" y OI Esférico "-1.75".
  2. Hacer click en "Firmar y completar consulta →" y llegar a la vista previa de la fórmula óptica.
  3. Revisar la tabla de valores en la fórmula generada.
- Esperado: OD Esférico = -2.00 / OI Esférico = -1.75 en sus respectivas filas.
- Observado: La fila OI aparece completamente vacía (todos los campos "—"). El valor -1.75 ingresado para OI Esférico aparece en la columna "Adición" de OD en lugar de en OI Esférico. Los datos de OI no se persisten o se mapean incorrectamente al generar el documento.
- Evidencia: Screenshot adjunto — tabla muestra OD: Esférico=-2.00, Adición=-1.75; fila OI: todos "—". El valor "-1.75" fue ingresado explícitamente en el campo OI Sphere del tab Prescripción.
- Estado: **investigado** (2026-04-28)
- Análisis: Verificado con curl — el backend Go guarda correctamente los campos (`sph_oi`, `add_od`, etc.) con JSON tags correctos. El repositorio usa nombres de columna explícitos que coinciden 1:1. El `PrescriptionTab` frontend usa nombres de campo dinámicos correctos (`sph_od`, `sph_oi`, etc.). El `PrescriptionPreviewPage` lee correctamente con acceso dinámico `rx.sph_oi`.
- El dato guardado en BD (appointment 9) muestra `sph_od: -2, add_od: -1.75, sph_oi: null`, lo que indica que el form envió `-1.75` bajo `add_od` en vez de `sph_oi`. La causa raíz no está en código estático — requiere debugging runtime con React Hook Form para verificar qué valores se envían realmente en `handleSubmit`.
- Próximo paso: Runtime debugging con `console.log` del formData antes del submit, o usar React DevTools para inspeccionar el estado del form.

### QA-008
- Rol: specialist
- URL: http://localhost:4300/specialist/appointments/:id/prescription-preview
- Severidad: sugerencia
- Pasos:
  1. Completar el formulario clínico.
  2. Hacer click en "Firmar y completar consulta →".
  3. Observar el título del modal de confirmación de firma.
- Esperado: El modal de firma de un documento legal debe usar un título formal y profesional, sin emojis.
- Observado: El título del modal es "🔒 Firmar fórmula óptica" — contiene un emoji (🔒) que resulta inapropiado para un contexto de documento con validez legal (Ley 650/2001 Art. 24). La ley aplica a fórmulas ópticas como documentos legales; el uso de emojis resta seriedad al flujo de firma.
- Evidencia: Screenshot adjunto — heading del modal muestra emoji visible.
- Estado: **resuelto** (2026-04-28)
- Fix: El código actual de `DigitalSignatureModal.tsx` usa `<Lock className="h-4 w-4 shrink-0" />` (Lucide SVG icon) en lugar de emoji `🔒`. El título es `<span>Firmar fórmula óptica</span>` sin emoji. El fix ya estaba implementado al momento de esta revisión.
