## Hallazgos (FAIL / GAP)

### QA-001
- **Rol:** admin
- **URL:** http://localhost:4300/admin/users/new
- **Severidad:** menor
- **Pasos:**
  1. Admin navega a Gestión → Usuarios → Nuevo Usuario
  2. Completa todos los campos con contraseña `password`
  3. Hace clic en "Crear Usuario"
- **Esperado:** El usuario se crea (la contraseña `password` es la credencial seed estándar del proyecto)
- **Observado:** El formulario muestra error de validación en el campo contraseña: _"Debe incluir letras y números"_ y no envía el formulario
- **Evidencia:** Validación Zod/RHF en UI — `paragraph [ref=e708]: Debe incluir letras y números` visible tras el submit
- **Estado:** confirmado
- **Impacto:** Las credenciales seed `password` documentadas en `docs/CREDENCIALES_PRUEBA_ROLES.md` no son usables al crear usuarios manualmente desde la UI admin. El equipo debe usar contraseñas alfanuméricas (ej. `password123`) o ajustar la validación de contraseña para que sea consistente con los seeders.

### QA-002
- **Rol:** receptionist (ana.qa@convision.com — asignada solo a Sede QA Test, branch_id=4)
- **URL:** http://localhost:4300/receptionist/dashboard (y todas las rutas /receptionist/*)
- **Severidad:** mayor
- **Pasos:**
  1. Admin crea usuario recepcionista con sede única: "Sede QA Test" (branch_id=4)
  2. Recepcionista inicia sesión con `ana.qa@convision.com`
  3. Observar el indicador de sede en sidebar y header
- **Esperado:** El sidebar y el header muestran "Sede QA Test" como sede activa
- **Observado:** El sidebar y el header muestran **"Sede Centro"** aunque todos los requests de red envían correctamente `X-Branch-ID: 4` (Sede QA Test)
- **Evidencia:** Network requests confirm `x-branch-id: 4` en appointments, sales/stats/today, daily-activity-reports. UI snapshot: `generic [ref=e922]: Sede Centro` en sidebar, `text: Sede Centro` en header.
- **Estado:** confirmado
- **Contexto técnico:** El localStorage almacena `convision_branch_id` del admin anterior (branch 3 = Sede Centro). Al hacer login como recepcionista, el sistema asigna correctamente el branch ID 4 para los requests de API (probablemente desde el primary branch del usuario), pero la etiqueta visible en UI lee el nombre del branch 3 desde localStorage sin actualizar al nombre del branch 4. El flujo de autenticación no limpia/actualiza el nombre de sede en localStorage al cambiar de usuario.

### QA-003
- **Rol:** receptionist (ana.qa@convision.com)
- **URL:** http://localhost:4300/receptionist/daily-report-history
- **Severidad:** mayor
- **Pasos:**
  1. Recepcionista entra a "Reporte de gestión diario" y completa el formulario (preguntas, cotizaciones, observaciones)
  2. Hace clic en "Guardar Reporte" → API responde 201 Created
  3. Navega a "Historial Reportes" para verificar el reporte guardado
- **Esperado:** El historial muestra el reporte recién guardado para 29/04/2026
- **Observado:** El historial muestra **un reporte de 28/04/2026** con 12 preguntas totales (de otra sesión/usuario), y el reporte recién creado para 29/04/2026 **no aparece**. El reporte SÍ es visible desde la vista admin (`/admin/daily-reports/1`)
- **Evidencia:**
  - `GET /api/v1/daily-activity-reports?page=1&per_page=15` → 200 OK con x-branch-id:4 → devuelve 28/04 (no 29/04)
  - `POST /api/v1/daily-activity-reports` → 201 Created → reporte creado
  - Admin en `/admin/daily-reports/1` confirma el reporte correcto de 29/04 con datos de Ana (preguntas H=5, M=7, obs="Reporte QA - primer día Sede QA Test")
- **Estado:** confirmado
- **Hipótesis causas:**
  1. El endpoint `GET /api/v1/daily-activity-reports` (historial recepcionista) filtra por user_id pero no discrimina entre reportes "borrador en edición" vs "guardados". El reporte de 29/04 puede estar en un estado no visible en historial hasta "Cerrar Reporte".
  2. El registro de 28/04 podría pertenecer a un usuario diferente pero devuelto porque el backend no filtra por `user_id` correctamente (devuelve todos los reportes del branch).
  3. El botón "Cerrar Reporte" estaba deshabilitado en el formulario, lo que puede ser condición para que el reporte aparezca en historial.
